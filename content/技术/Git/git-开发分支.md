在团队协作中，**开发分支**（Development Branches）是代码协作的核心载体。它们不仅承载着不同阶段的代码变更，更定义了整个团队的协作节奏与发布流程。合理的分支策略能让多人并行开发井然有序，而混乱的分支管理则会引发合并冲突、发布延迟甚至线上事故。

本文系统梳理常见的分支模型、命名规范以及管理最佳实践，帮助团队建立清晰、可扩展的分支管理体系。

### 一、常见分支模型

#### 1. Git Flow（经典模型）

由 Vincent Driessen 于 2010 年提出，是最具影响力的分支模型，适用于有固定发布周期的项目。

| 分支类型     | 名称          | 作用               | 生命周期                                      |
| -------- | ----------- | ---------------- | ----------------------------------------- |
| **常驻分支** | `main`      | 生产环境代码，随时可发布     | 永久                                        |
| **常驻分支** | `develop`   | 日常开发集成分支，包含最新功能  | 永久                                        |
| **临时分支** | `feature/*` | 新功能开发            | 完成后合并回 `develop` 并删除                      |
| **临时分支** | `release/*` | 发布准备（测试、修复小 Bug） | 完成后合并到 `main` 和 `develop` 并删除             |
| **临时分支** | `hotfix/*`  | 紧急修复线上 Bug       | 完成后合并到 `main` 和 `develop`（或 `release`）并删除 |

**特点**：

- 严格区分功能、发布、修复三类临时分支
- 适合需要多版本并行维护的复杂项目
- 缺点：分支多、操作繁琐，不适合持续交付

#### 2. GitHub Flow（简化模型）

由 GitHub 推广的轻量级模型，适用于持续部署和快速迭代。

|分支类型|名称|作用|生命周期|
|---|---|---|---|
|**常驻分支**| `main` |唯一长期分支，始终可部署|永久|
|**临时分支**| `feature/*` 或 `fix/*` |任何变更（功能、修复、重构等）|完成后通过 PR 合并到 `main` 并删除|

**特点**：

- 只有一个常驻分支 `main`
- 所有变更都从 `main` 拉出新分支，完成后发起 Pull Request
- 通过 [[CI]] 自动测试，合并后自动部署
- 适合 web 应用等频繁部署的场景

#### 3. GitLab Flow（环境分支模型）

在 GitLab Flow 中，除了 `main`，还会引入与环境对应的长期分支。

|分支类型|名称|作用|
|---|---|---|
|**常驻分支**| `main` |最新开发代码|
|**环境分支**| `staging` |预发布环境，进行集成测试|
|**环境分支**| `production` |生产环境代码（与 `main` 同步）|

**特点**：

- 每次部署到不同环境时，将代码推送到对应分支（如 `staging`、`production`）
- 若环境需要回滚，只需将旧版本强制推送到环境分支
- 结合 CI/CD，形成“分支即环境”的理念

#### 4. Trunk-Based Development（主干开发）

强调极短的分支生命周期，所有开发者直接在 `main` 上协作，或使用极短存活期的特性分支。

|分支类型|名称|作用|
|---|---|---|
|**唯一常驻**| `main`（或 `trunk`）|所有变更直接提交或通过极短期分支合并|
|**短期分支**| `feature/*` |通常不超过一天，频繁合并回 `main` |

**特点**：

- 极高的 CI 频率，要求代码质量高
- 减少合并冲突，适合成熟团队
- 结合特性开关（Feature Toggle）控制未完成功能

### 二、分支命名规范

无论采用哪种模型，一致的分支命名规则都能提升可读性和追踪效率。推荐使用 **前缀 + 描述** 的结构，描述中可包含 Issue 编号。

#### 1. 常用前缀

| 前缀            | 用途             | 示例                          |
| ------------- | -------------- | --------------------------- |
| `feature/`    | 新功能开发          | `feature/user-profile-page` |
| `fix/`        | Bug 修复（非紧急）    | `fix/password-validation`   |
| `hotfix/`     | 紧急线上修复         | `hotfix/payment-timeout`    |
| `release/`    | 发布准备           | `release/v1.2.0`            |
| `docs/`       | 文档更新           | `docs/api-readme`           |
| `chore/`      | 维护任务（依赖升级、配置等） | `chore/update-dependencies` |
| `experiment/` | 实验性功能（未必合并）    | `experiment/new-algorithm`  |

#### 2. 包含 Issue 编号

在大型项目中，推荐在分支名中关联 Issue 跟踪系统：

```text
<prefix>/<issue-id>-<short-description>
```

示例：
- `feature/GH-1234-add-oauth-login`
- `fix/JIRA-567-fix-null-pointer`

这样通过分支名即可快速定位问题来源，也便于自动化工具关联 PR 与 Issue。

#### 3. 命名注意事项

- **使用小写字母和连字符（`-`）**，避免使用下划线或驼峰，保持跨平台一致性。
- **描述要简洁且含义清晰**，避免过长（建议 3~6 个单词）。
- **避免使用 `master`** 等可能有争议的历史名称，统一使用 `main`。
- **禁止包含特殊字符**（如 `~`、`^`、`:` 等），以免影响 Git 和 CI 系统。

### 三、分支管理最佳实践

#### 1. 保护长期分支

对 `main` 和 `develop` 等长期分支开启分支保护规则：

- 禁止直接推送（必须通过 PR/MR）
- 要求至少一名审查者批准
- 要求 [[CI]] 状态检查通过
- 禁止强制推送（`--force`）

#### 2. 合并策略选择

- **Merge Commit**：保留完整历史，但可能产生“章鱼”图，适合复杂发布场景。
- **Squash Merge**：将 PR 中的所有提交压缩为一个提交，历史更整洁，适合 GitHub Flow。
- **Rebase Merge**：将分支提交变基到目标分支，线性历史，但需谨慎处理冲突。

#### 3. 及时清理已合并分支

合并后应立即删除远程和本地的临时分支，避免堆积：

```bash
# 删除本地分支
git branch -d feature/xxx
# 删除远程分支
git push origin --delete feature/xxx
```

- 许多 Git 托管平台支持在 PR 合并后自动删除源分支，建议开启此功能。

#### 4. 保持分支与上游同步

长期开发的 `feature` 分支应定期从基础分支（`develop` 或 `main`）拉取最新代码，并使用 `rebase` 保持历史线性（若团队偏好）。同步频率建议每 1~2 天一次，避免最终合并时冲突过大。

#### 5. 使用 git hook 或 [[CI]] 进行校验

在提交或推送时，可借助 `pre-commit` 或 CI 检查分支命名是否符合规范，例如通过正则表达式验证：
```regex
^(feature|fix|hotfix|release|docs|chore)/[a-z 0-9-]+$
```

这样在源头就能杜绝不规则分支名进入仓库。

### 四、如何选择适合团队的分支模型？

| 团队情况                      | 推荐模型                      |
| ------------------------- | ------------------------- |
| 传统企业、固定发布周期（如按月发布）        | Git Flow                  |
| 互联网 SaaS、每日多次部署           | GitHub Flow 或 Trunk-Based |
| 有多个环境（测试、预发布、生产）且需要精确控制版本 | GitLab Flow（环境分支）         |
| 成熟敏捷团队，自动化程度高             | Trunk-Based Development   |
|                           |                           |


无论选择哪种，**统一规范**和**工具自动化**是关键。将分支策略写入 `CONTRIBUTING.md`，并结合 CI/CD 流水线强制执行，才能让分支管理真正成为效率工具而非负担。
